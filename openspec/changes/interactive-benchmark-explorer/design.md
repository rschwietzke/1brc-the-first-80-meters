## Context

The 1BRC project's benchmark harness produces CSV and JSON metadata files in `data/benchmark-history/`. Each CSV row contains 7 dimension columns (JDK, GC_OPTS, VM_OPTS, PROG_OPTS, BINDING, DATA, Class) and 14+ metric columns. There are currently 4 complete benchmark runs with 48–192 permutations each. The existing static HTML reports (generated by FreeMarker) show all metrics as `0 ms` and offer no interactivity.

The root `pom.xml` already has `<module>benchmark-viewer</module>` commented out, indicating this module was always planned. The project targets Java 25, but the benchmark-harness uses Java 21. We'll target Java 21 for maximum compatibility.

The user has prior experience with Spring Boot + HTMX + Bootstrap stacks (evidenced by the posters-demo-store and XTC projects in their workspace), making this a natural technology choice.

## Goals / Non-Goals

**Goals:**
- Build a Spring Boot 4 web application as a new Maven module (`benchmark-viewer`).
- Import CSV data into an H2 embedded database at startup, with JPA entities modelling the domain.
- Index all measurement data with Hibernate Search 7.x (Lucene backend) for fast faceted aggregations.
- Render all UI with Thymeleaf + Bootstrap 5, using HTMX for partial page swaps and dynamic filtering.
- Provide hierarchical drill-down: Test Runs → Variations matrix → Variation timeline → Execution detail.
- Focus on **comparative trend analysis and anomaly detection** — reveal how the same class behaves across different JDKs, GCs, and heap sizes, and surface unexpected changes.
- Provide **side-by-side environment comparison** with percentage deltas to visually surface regressions and improvements when varying a single dimension.
- Compute and display **derived counter metrics** (branch miss rate, L1 miss rate, CPI) conditionally — only when the underlying hardware counters are present in the data.
- Surface **hidden performance signals** — detect and highlight cases where runtime is stable but hardware counters shift significantly, indicating compensated degradation.
- Offer **JFR file download links** in the execution detail view when `.jfr` profiling files exist for a measurement.
- Provide a **heat coloring normalization toggle** in the variation matrix (per-column vs global scaling).
- Visually **flag ERROR measurements** distinctly in the matrix view — greyed out or with clear error indicators, never showing misleading `0 ms` values in normal styling.
- Serve JSON endpoints for ECharts visualizations (bar charts, line charts).
- Support re-importing data without restarting (via a "Reimport" action).

**Non-Goals:**
- No production deployment or cloud infrastructure — this is a local diagnostic tool (`localhost:8080`).
- No user authentication or multi-tenancy.
- No modification of the benchmark harness or its CSV output format.
- No modification of the existing static HTML reports.
- No automated regression detection (that's the `jdk-regression-report` capability).
- No optimization progression charts based on class naming conventions (e.g. BRC001 → BRC050 step ordering).
- No friendly label aliasing for raw JVM flags — this is an expert tool; raw flags like `-XX:+UseZGC` are displayed as-is.
- No stable URL sharing system — URL deep-linking via `hx-push-url` is best-effort for local use only.

## Decisions

1. **Spring Boot 4 + H2 + Hibernate Search 7.x**
   - *Decision:* Use Spring Boot as the application framework, H2 as an embedded database (file-mode for persistence between restarts), and Hibernate Search 7.x with the Lucene backend for indexing and faceted search.
   - *Rationale:* Spring Boot provides rapid development. H2 eliminates external DB setup. Hibernate Search's faceted aggregations are significantly faster than SQL `GROUP BY` for multi-dimensional filtering — this is critical for the faceted sidebar experience.
   - *Alternative considered:* Pure client-side with CSV parsing in JavaScript — rejected because the user explicitly wants a Spring Boot application with a database and indexing capabilities.

2. **Thymeleaf + HTMX for server-rendered partials**
   - *Decision:* Use Thymeleaf as the template engine with HTMX for dynamic partial page swaps. No client-side SPA framework.
   - *Rationale:* HTMX keeps the server as the single source of truth for UI state. Sidebar filter changes trigger `hx-get` requests that return updated Thymeleaf fragments, swapping only the main content area. This avoids complex client-side state management while delivering a responsive UX.
   - *Alternative considered:* React/Vue SPA with REST API — rejected because it adds a JavaScript build pipeline and duplicates domain logic on the client.

3. **Bootstrap 5 for styling**
   - *Decision:* Use Bootstrap 5 from CDN for layout, components, and responsive design. Use Bootstrap's default light theme for the premium appearance.
   - *Rationale:* Bootstrap provides a rich component library (cards, tables, badges, navs, offcanvas) out of the box, reducing custom CSS effort.

4. **Domain model: TestRun → Measurement**
   - *Decision:* Two JPA entities: `TestRun` (timestamp, machine info, total count) and `Measurement` (all CSV columns: JDK, GC, VM opts, prog opts, binding, dataset, class, + all metric fields). `Measurement` has a `@ManyToOne` to `TestRun`.
   - *Rationale:* The CSV data naturally groups by timestamp into runs. Measurements are the atomic unit for filtering and comparison. Hibernate Search indexes the dimension fields on `Measurement` for faceted aggregation.

5. **CSV import on startup**
   - *Decision:* A `CommandLineRunner` or `@PostConstruct` service scans `data/benchmark-history/` for `*-meta.json` files, creates `TestRun` entities, then parses the corresponding `.csv` files into `Measurement` entities. Old-format CSVs (with `TASKSET` instead of `BINDING`) are handled with column-name fallback logic mirroring `ResultMatrix.java`.
   - *Rationale:* Importing at startup keeps the data layer simple. H2 file-mode means subsequent starts can skip re-import if data hasn't changed (check against existing timestamps).

6. **ECharts via JSON endpoints**
   - *Decision:* The Spring controllers expose `@GetMapping` endpoints returning JSON data formatted for ECharts consumption. Thymeleaf templates include `<script>` blocks that fetch these endpoints and initialize ECharts instances.
   - *Rationale:* This cleanly separates data (JSON) from presentation (Thymeleaf). ECharts initialization in the browser is the only significant client-side JavaScript.

7. **HTMX navigation pattern**
   - *Decision:* The main page has a fixed layout (sidebar + breadcrumb + main content). Navigation (clicking a run, a matrix cell, etc.) uses `hx-get` to fetch a Thymeleaf fragment and `hx-target="#main-content"` to swap the main area. Breadcrumbs and URL are updated via `hx-push-url`.
   - *Rationale:* This gives SPA-like navigation without JavaScript routing. Deep links work because the same controller methods handle both full page loads and HTMX fragment requests (using `HX-Request` header detection).

8. **Side-by-side environment comparison**
   - *Decision:* Provide a comparison view where the user selects two environment configurations (e.g. "JDK 21 + ZGC + 2G" vs "JDK 25 + ZGC + 2G") and sees all classes side by side with both runtimes and a percentage delta column. Positive delta = regression (red), negative delta = improvement (green). Optionally, a scatter plot overlay (X = env A, Y = env B, diagonal = parity) for visual anomaly spotting.
   - *Rationale:* The core use case is dimensional comparison — holding everything else constant, varying one dimension, and immediately seeing what moved and by how much.

9. **Conditional derived counter metrics**
   - *Decision:* Compute and display derived metrics (branch miss rate = `BranchMisses / Branches`, L1 miss rate = `L1Misses / Instructions`, CPI = `Cycles / Instructions`) only when the underlying raw counters are non-zero and present. Columns with entirely missing data are hidden, not shown as empty.
   - *Rationale:* Not all hardware setups deliver perf counters. The UI must gracefully degrade — showing only what's available rather than rendering empty columns.

10. **Hidden performance signal detection**
    - *Decision:* When runtime is stable across two measurements but hardware counters shift significantly (e.g. branch misses doubled, IPC dropped >15%), surface this as a visual indicator in the comparison and timeline views. Exact thresholds TBD during implementation.
    - *Rationale:* A CPU may compensate for a degraded code path via frequency scaling or speculative execution. The runtime looks fine, but the workload is actually worse — this is the class of regression that only hardware counters reveal.

11. **ERROR measurement visual flagging**
    - *Decision:* Measurements with `Checksum = "ERROR"` are imported with `error = true`. In the variation matrix, ERROR cells are rendered with distinct visual treatment (greyed out, strikethrough, or error badge) — never displayed as normal `0 ms` values.
    - *Rationale:* ERROR rows contain valid hardware counter data (cost of the failure path), but displaying them as `0 ms` in normal styling would be misleading.

12. **Heat coloring normalization toggle**
    - *Decision:* The variation matrix supports two heat coloring modes toggled by the user: (a) per-column normalization — green-to-red scaled relative to the min/max within each class column, and (b) global normalization — the same color represents the same runtime across all cells.
    - *Rationale:* Per-column shows relative performance within one class across environments. Global shows absolute scale across classes, preserving cross-class comparability.

13. **JFR file download links**
    - *Decision:* In the execution detail view, if a `.jfr` profiling file exists for the measurement's configuration (matched by class, JDK, GC, heap, and run timestamp), display a download link. The file is served directly from the `data/benchmark-history/` directory tree.
    - *Rationale:* JFR profiles are the next-level diagnostic tool. Linking directly to the file lets the user open it in JMC or IntelliJ without hunting through directories.

## Risks / Trade-offs

- **Risk: Startup import time for large datasets** → Current data is < 1000 rows total (4 runs × ~200 permutations). Even at 10,000 rows, H2 bulk insert is sub-second. If it grows to 100K+, we can add lazy loading per-run.

- **Risk: H2 file locking** → H2 in file mode locks the database file. Only one instance of the viewer can run at a time. Acceptable for a local tool.

- **Risk: Hibernate Search Lucene index corruption on unclean shutdown** → Mitigation: The index is fully reconstructable from the database. A "Reindex" admin action can rebuild it.

- **Trade-off: H2 vs PostgreSQL** → H2 means zero setup but limited query features. For a local diagnostic tool, this is the right trade-off. If we ever need full-text SQL queries or complex analytics, we can swap to PostgreSQL with a profile.

- **Trade-off: CDN dependencies for Bootstrap/ECharts/HTMX** → Local development requires internet for the first load, then browser cache covers it. We can vendor the files later if full offline support is needed.

### Entity Design: Two Entities (Flat)

```
┌─────────────────┐         ┌─────────────────────────────────┐
│    TestRun      │         │         Measurement             │
├─────────────────┤         ├─────────────────────────────────┤
│ id (PK, auto)   │ 1    * │ id (PK, auto)                   │
│ timestamp       │────────│ testRun (@ManyToOne)             │
│ totalRuns       │         │ runTimestamp (denormalized)      │
│ comment         │         │                                 │
│                 │         │ ── Dimensions ──────────────── │
│ ── Machine ──  │         │ jdk          (@KeywordField)    │
│ hostname        │         │ gcOpts       (@KeywordField)    │
│ kernelVersion   │         │ vmOpts       (@KeywordField)    │
│ os              │         │ progOpts     (@KeywordField)    │
│ cpu             │         │ binding      (@KeywordField)    │
│ cpuCores        │         │ dataset      (@KeywordField)    │
│ memory          │         │ className    (@KeywordField)    │
│                 │         │                                 │

                            │ perfRuntimeMs       (long)      │
                            │ jfrRuntimeMs        (long)      │
                            │ instructions        (long)      │
                            │ cycles              (long)      │
                            │ branches            (long)      │
                            │ branchMisses        (long)      │
                            │ l1Misses            (long)      │
                            │ llcMisses           (long)      │
                            │ pageFaults          (long)      │
                            │ taskClock           (long)      │
                            │ contextSwitches     (long)      │
                            │ cpuMigrations       (long)      │
                            │ ipc                 (double)    │
                            │ secElapsed          (double)    │
                            │ secUser             (double)    │
                            │ secSys              (double)    │
                            └─────────────────────────────────┘
```

**Why flat and not normalized:** The dimension cardinality is tiny (2 JDKs, 3 GCs, 3 heaps, 68 classes). Normalizing dimensions into separate tables would add join complexity with zero storage benefit at ~1,200 rows per run. Each CSV row maps 1:1 to a `Measurement` entity, keeping the import trivial and Hibernate Search faceting operating on a single entity without `@IndexedEmbedded` indirection.

**Alternative considered (three entities with Environment normalization):** Extracting JDK+GC+heap+prog+binding into an `Environment` entity was considered but rejected — it complicates Hibernate Search indexing (facets would need `@IndexedEmbedded` to reach through to `Environment` fields), makes the import two-phase, and saves nothing at this data volume.

## Hibernate Search Indexing Strategy

### Indexed Entity: `Measurement`

All 7 dimension columns are annotated with `@KeywordField` on the `Measurement` entity. Metric columns are **not** indexed in Lucene — they are only queried via JPA for display and chart endpoints.

**Why `@KeywordField`:** The dimension values are exact tokens (`"JDK_21_OPEN"`, `"-XX:+UseZGC"`) — never searched by substring or analyzed. They are used exclusively for exact-match filtering and terms aggregation (facet counts). `@KeywordField` stores each value as a single unanalyzed token, which is exactly what faceting requires.

**Why metrics are not indexed:** Metrics (instructions, cycles, IPC, etc.) are only displayed in detail views (fetched by entity ID) or used in chart JSON endpoints (fetched by JPA queries with WHERE clauses on dimensions). Indexing them in Lucene would bloat the index for zero query benefit.

### Faceted Search Flow

```
User toggles "ZGC" checkbox in sidebar
  → HTMX GET /sidebar?jdk=JDK_21_OPEN&gcOpts=-XX:+UseZGC
  → SearchService.getFacetCounts(activeFilters)
     → Hibernate Search: bool query with must(match jdk), must(match gcOpts)
     → Terms aggregation on all 7 dimension fields
     → Returns Map<String, Map<String, Long>>
        e.g. { "gcOpts": {"ZGC": 408, "G1": 408, "Serial": 408},
               "vmOpts": {"1g": 204, "2g": 204, "4g": 204},
               "className": {"BRC001": 6, "BRC010": 6, ...} }
  → Sidebar re-rendered with updated counts and active checkmarks
  → Main content re-fetched with same filters applied
```

## Import Pipeline

### Import Sequence

1. Scan `data/benchmark-history/` for `*-meta.json` files
2. For each meta.json, extract the timestamp
3. Check if a `TestRun` with that timestamp already exists → skip if yes
4. Parse `*-sysinfo.txt` (line-by-line `Key: Value` format)
5. Create and persist `TestRun`
6. Parse `*.csv` using a proper CSV parser (OpenCSV or Apache Commons CSV) to handle quoted fields containing commas (e.g. `"-Xms1g -Xmx1g"`)
7. For each data row: create `Measurement`, set `testRun` reference, persist
8. After all runs imported: trigger Hibernate Search mass indexer

> **CSV parsing note:** The `GC_OPTS`, `VM_OPTS`, `PROG_OPTS`, and `BINDING` columns contain quoted values with spaces (e.g. `"-Xms1g -Xmx1g"`, `"taskset -c 0-7"`). A naive `String.split(",")` will break inside these quotes. The import must use a proper CSV parser or strip/handle quotes manually.

## Open Questions

> **Q1: Class name storage — full or simple?**
> The CSV stores fully qualified class names (`org.onebrc.again26.BRC001_Baseline`). The package is always `org.onebrc.again26`. For display we'd show `BRC001_Baseline`. Options:
> - (a) Store the full name, derive the simple name via a transient getter
> - (b) Store both `className` (full) and `simpleClassName` (display) as separate fields
> - (c) Store only the simple name
>
> Recommendation: (a) — store full, derive simple. Keeps a single source of truth.
>
> **Decision:** (a) — Store full class name, derive simple name via transient getter. Same simple name can exist across different packages, so the full qualified name is the required unique identifier.

> **Q2: Denormalize `runTimestamp` onto `Measurement`?**
> Timeline queries need to find measurements for a given class+environment across runs, ordered by timestamp. The `RunTimestamp` column already exists in every CSV row. Options:
> - (a) Denormalize: store `runTimestamp` on `Measurement` too — simplifies JPA and Lucene queries
> - (b) Always join through `testRun` relationship
>
> Recommendation: (a) — the data is already there in the CSV, costs nothing, simplifies queries.
>
> **Decision:** (a) — Denormalize. Store `runTimestamp` on `Measurement` directly. The data is already in every CSV row, costs nothing, and avoids JOINs in timeline queries.

> **Q3: How to handle `Checksum = "ERROR"` rows?**
> Some classes failed during execution (e.g. `BRC025_MutateData`, `BRC090_MemorySegment_VOID`). Their `MedianRuntimeMs` is `0` and `Checksum` is `"ERROR"`, but the perf counters (instructions, cycles, IPC) are still valid. Options:
> - (a) Import them with a boolean `error` field — perf data shows cost of the failure path
> - (b) Skip them entirely during import
>
> Recommendation: (a) — the hardware counter data is still valuable.
>
> **Decision:** (a) — Import with `error = true` flag. Hardware counter data from failed runs is valuable for diagnosing the failure path (e.g. GC thrashing, OOM patterns).

> **Q4: Should `RunTimestamp` be a sidebar facet dimension?**
> With multiple runs, the user might want to filter by run. But this conflicts with timeline views which inherently span runs. Options:
> - (a) Keep run selection as separate navigation (the Test Run list page), not a sidebar facet
> - (b) Add it as an 8th facet dimension in the sidebar
>
> Recommendation: (a) — run selection is a navigation concern, not a filter concern.
>
> **Decision:** (a) — Keep run selection as navigation, not a facet. Runs are a context, not a filter dimension.
